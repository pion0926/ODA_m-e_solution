# K-ODAME 풀테스트 계획

## 목적

관리자 화면에서 다국어 독립 프로젝트를 생성하고 수행자 계정을 배정하는 단계부터 71개 사업문서 업로드, 문서별 분석·DB 저장, PDM/사업정보 갱신, PDM·DAC 분류, 성과지표 갱신, DAC 재평가, 27개 보고서 자동작성과 HWPX 산출까지 실제 사용자 흐름을 종단 간 검증한다.

풀테스트는 단순 화면 확인이 아니다. 각 단계의 UI 결과와 API/DB 상태, 다음 단계에 전달되는 데이터의 연결성을 함께 검증한다. 2026-08-29까지 누적된 사용자 우려사항은 `user-concern-regression-testset.md`를 필수 릴리스 게이트로 함께 실행한다.

## 실행 트리거

사용자가 “풀테스트”, “전체 흐름 테스트”, “종단 간 테스트”를 요청하면 본 계획을 실행한다. 단순 화면 QA 요청은 `ui-regression-testset.md`만 실행한다.

## 실행 원칙

- 매 실행마다 고유 `run_id`를 `FT-YYYYMMDD-HHMMSS` 형식으로 만든다.
- 기존 공용 프로젝트나 `test1`~`test10` 프로젝트 데이터를 재사용하지 않는다.
- 풀테스트용 일반 계정을 준비하고, 관리자 화면의 `새 프로젝트`에서 해당 계정을 참여 계정으로 선택한다.
- 관리자는 신규 프로젝트의 `owner`, 선택 계정은 `viewer`(수행자)로 자동 배정되는 실제 정책을 유지한다. 역할상 실행할 수 없는 후속 단계는 관리자 소유 세션으로 이어서 검증하고 그 전환을 결과에 기록한다.
- 기본 풀테스트 프로젝트는 5개 언어(`ko`, `en`, `vi`, `ru`, `uz`)를 모두 제공하고 기본 언어는 `ko`로 생성한다. 언어별 경계값은 별도 TC에서 검증한다.
- 생성된 계정 비밀번호는 저장소 문서에 기록하지 않는다. 실행 종료 후 사용자에게 결과와 함께 직접 공유한다.
- 입력자료는 `full-test-corpus.md`의 71개 파일을 사용한다.
- 업로드, 지표 갱신, 재평가, 보고서 생성처럼 외부 비용과 데이터 변경이 발생하는 작업은 풀테스트 요청 범위 안에서만 실행한다.
- 실패해도 후속 단계를 억지로 통과시키지 않는다. 선행조건 실패로 인한 후속 항목은 `BLOCKED`로 기록한다.
- 테스트 프로젝트는 결과 확인을 위해 자동 삭제하지 않는다. 사용자가 삭제를 요청할 때만 정리한다.
- 명시적 로그인 성공 후에는 이전 URL hash와 관계없이 항상 `/#/dashboard`에서 사용자 흐름을 시작한다. 세션 복원과 화면 새로고침은 현재 딥링크를 유지하는 별도 시나리오로 판정한다.
- 업로드 문서는 사용자 승인이나 수동 배정 없이 PDM·DAC 슬롯에 자동 배정한다. 증빙이 아닌 안내 파일만 `증빙 슬롯 해당 없음`으로 구분하며 `미배정` 또는 `수동 배정 필요` 상태를 정상 상태로 인정하지 않는다.
- 사업개요의 PDM 근거는 현재 PDM 모델이 선택한 가장 최신 유효 PDM 1건만 노출한다.
- 종료평가 분석과 점수는 적절성·일관성·효과성·효율성·지속가능성의 DAC 5개 기준으로만 구성하며 `영향`을 평가 기준으로 추가하지 않는다.

| 상태 | 의미 |
|---|---|

## Phase 1 — 관리자 다국어 프로젝트 생성·계정 배정·격리

프로젝트는 반드시 관리자 화면의 `새 프로젝트`로 생성한다. 테스트 준비 도구나 DB 직접 입력은 정상 흐름의 대체 수단으로 사용하지 않는다. 기본 시나리오는 5개 언어를 모두 선택하고 `ko`를 기본 언어로 지정하며, 경계값 TC는 별도의 폐기 가능한 프로젝트로 실행한다.

## Phase 1A — 프로젝트별 다국어 선택·번역·저장

아래 TC는 본 프로젝트의 두 수행자 계정으로 실행한다. 언어 전환마다 `/#/dashboard`부터 전체 사용자 화면을 순회하며 번역 대상과 원문 데이터의 경계를 함께 확인한다.

| TC | 검증 내용 | 절차 | 합격 기준 |
|---|---|---|---|
| FT-01A01 | 언어 드롭다운 범위 | 수행자 계정에서 드롭다운 열기 | 프로젝트의 5개 제공 언어만 표시, 중복·미지원 언어 없음 |
| FT-01A02 | 5개 언어 전환 | `ko→en→vi→ru→uz` 순서로 선택 | 선택 즉시 메뉴·그룹·대시보드·주요 화면 제목이 해당 언어로 갱신 |
| FT-01A03 | 한국어 렌더링 | `ko`에서 전체 화면 순회 | 한글 자모 분리, `�`, 잘못 디코딩된 문자열, 원시 번역 키 없음 |

| FT-01A05 | 베트남어 렌더링 | `vi`에서 전체 화면 순회 | 성조 부호가 정상 렌더링되고 대체문자·잘림 없음 |
| FT-01A06 | 러시아어 렌더링 | `ru`에서 전체 화면 순회 | 키릴 문자가 정상 렌더링되고 대체문자·잘림 없음 |

## Phase 7 — 27개 섹션별 보고서 평가·HWPX·rhwp 최종 확인

보고서 단계는 생성 API 성공이나 글자 수만으로 통과시키지 않는다. 보고서 편집 화면에서 27개 섹션을 각각 평가한 뒤, 전 섹션이 통과한 경우에만 HWPX를 저장한다. 저장된 최신 HWPX를 rhwp 미리보기로 다시 열어 원본 양식의 문단·표·페이지 배치를 최종 확인한다.

구성과 출처 표기는 `sample-report-composition-standard.md`를 적용한다. `samples`의 완성형 종료평가 보고서 5건에서 확인한 목차·장/절 계층·평가매트릭스·환류 표·출처 표기 관행을 비교 기준으로 사용하며, 샘플 사업의 문장·수치·기관을 현재 프로젝트 본문에 복사하지 않는다.

각 섹션은 다음 공통 항목을 개별 기록한다.

- `내용`: 섹션 목적과 전용 작성지시에 맞는 내용인지, 다른 섹션 내용을 반복하거나 대신 작성하지 않았는지
- `근거`: 허용된 현재 프로젝트 문서·PDM·성과지표·DAC 결과를 사용하고 수치와 판단을 추적할 수 있는지
- `구조`: 제목·소제목·문단·목록·표의 순서와 필수 항목이 원본 양식 및 해당 섹션 adapter 계약과 일치하는지
- `양식`: 원본 템플릿의 들여쓰기 단계, 문단 정렬, 줄간격, 글머리 기호, 번호 체계, 표 셀 위치·정렬·병합이 보존되는지
- `문자`: 원시 Markdown 기호(`#`, `**`, 백틱, 표 파이프), 내부 작업표시, 깨진 글자, 내부 UUID가 최종 HWPX에 노출되지 않는지
- `시각`: rhwp 미리보기에서 잘림·겹침·고아 제목·비정상 빈 페이지·표의 페이지 이탈 없이 읽을 수 있는지
- `출처 표현`: 원본 추적 metadata는 유지하되 제출 본문에는 업로드 파일명·확장자·경로·밑줄·업로드일·UUID를 노출하지 않고 사람이 읽는 문서명/기관명·연도·필요한 쪽수로 표현하는지

들여쓰기와 기호는 생성 본문의 공백 개수만 보는 것이 아니라 HWPX 결과의 문단 속성으로 판정한다. 제목/본문/하위목록의 계층이 원본 양식과 같고, 동일 계층에서 같은 기호 체계를 사용하며, 하위 항목은 상위 항목보다 깊게 들여쓰기되어야 한다.

- 문서 처리 실패가 1건 이상 남음

- 사업개요에 최신 PDM 외 구버전 PDM이 근거로 함께 노출됨
- 증빙 문서가 pending·미배정·수동 배정 필요 상태로 남음
- 성과지표 갱신 실패
- 지표 갱신 결과에 구체적인 위험 분석 또는 실행 가능한 개선권고가 없음

- 대시보드 KPI 14개 펼치기·임계색 또는 PDM/DAC AI 할 일 원천·이동이 잘못됨
- DAC 평가 실패 또는 질문 결과 누락
- 종료평가 분석에 `영향`이 별도 기준으로 포함됨
- 보고서에 다른 사업 사실이 포함됨
- 27개 섹션 중 하나라도 내용·근거·구조·양식 개별 평가가 누락되거나 FAIL
- 27개 텍스트 생성 계약과 27개 HWPX 적용 계약의 54개 1:1 대응이 깨지거나 few-shot 형식 전용 규칙이 누락됨
- HWPX 저장 실패, 원시 Markdown 기호 잔존 또는 템플릿 문단·표 구조 훼손
- 성과달성도 입력 행 누락, 등급표 1쪽 조판 실패, 목차 점선·쪽수 누락, 평가개요 계층 공백·기호 불일치가 발견됨
- rhwp 미리보기에서 최신 HWPX를 열지 못하거나 섹션 누락·잘림·겹침·글자 깨짐 발견

중단 기준 발생 시 데이터 손상을 피하기 위해 다음 비용성 단계를 실행하지 않고 결과를 `FAIL/BLOCKED`로 보고한다.
