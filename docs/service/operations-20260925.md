# 운영·배포·복구 절차

## 환경별 명령

개발은 루트 `docker-compose.yml`, 합성 QA는 `compose.qa.yml`을 사용한다.
운영은 `.runtime/production-release.json`의 **고정 릴리스 소스와 이미지 ID**를 사용한다.
운영을 현재 작업 디렉터리로 직접 실행하거나 `down -v`로 종료하지 않는다.

```powershell
./tools/ops/Server.ps1 -Environment development -Action status
./tools/ops/Server.ps1 -Environment production -Action status
./tools/ops/Test-Service.ps1
docker compose -f compose.qa.yml up -d --no-build --wait --wait-timeout 180
```

키·비밀번호·전체 Compose 환경 출력을 로그/이슈에 공유하지 않는다.

## 릴리스 순서

1. 변경·프롬프트·회귀 검사·QA 결과를 검토한다. 이전부터의 미커밋 변경이 있으므로 무조건 `git add .`로 묶지 않는다.
2. 운영 보관 정책에 따른 DB·파일 백업을 확보한다. 다른 저장소 복제는 해당 데이터 반출 권한이 필요하다.
3. 활성 업로드·평가·보고서·내보내기가 없는 시점을 확인한다. 구 API의 메모리 작업 실행 중 버전을 바꾸지 않는다.
4. 검증한 이미지를 불변 ID로 고정한다. `tools/ops/Promote-ValidatedRelease.ps1`의 검증·릴리스 절차를 사용한다.
5. 마이그레이션 → API → 워커/웹 시작 순서를 지킨다. API와 등록 1개·분석 2개·보고서 2개 워커는 같은 API 이미지를 사용한다.
6. 내부 건강 상태와 **공개 HTTPS 주소**·세션·업로드 목록·지표·보고서 읽기 API를 점검한다. 운영 원본을 테스트 목적으로 재분석하지 않는다.

웹은 비특권 nginx UID로 8080과 80을 함께 수신한다. 호스트 포트는 8080에 연결하고 기존 Cloudflare 터널은 Docker 내부 80에 연결한다.
Docker의 `net.ipv4.ip_unprivileged_port_start=0` 환경에서 양쪽 포트 응답을 검증했다. 컨테이너 healthy만으로 공개 터널 연결을 확인했다고 판단하지 않는다.

롤백 전에도 큐를 비워야 한다. 구 API는 새 영속 큐를 처리하지 못한다.
추가 테이블·열은 삭제하지 않고 남길 수 있으나 구/신 API·워커를 혼용하지 않는다.

## 상태와 장애 대응

- `docker compose ps`: DB/API/변환/다섯 워커/웹이 healthy, migrator와 파일 권한 초기화는 종료 코드 0이 기대값이다.
- API 컨테이너의 `/healthz`: API/DB 확인이며 워커까지 정상이라는 의미는 아니다. 웹 주소의 `/healthz`는 Nginx 생존 확인이다.
- 관리자 `GET /api/v2/admin/runtime`: 큐별 상태·가장 오래 대기한 시간·업로드 상태·프롬프트 지문.
- `X-Request-ID`로 HTTP 로그를 찾고 workflow ID로 워커 로그를 연결한다.
- heartbeat는 프로세스/리더 DB 연결 확인이다. 개별 외부 요청이 진전되고 있다는 보장은 아니다.

| 상황 | 처리 |
| --- | --- |
| API 재시작 | DB 대기 작업 유지; 업무 상태를 일괄 실패로 바꾸지 않는다. |
| 워커 중단 | 다음 리더가 중단을 표시; 기존 결과 보존 후 사용자가 재실행한다. |
| 보고서 일부 실패 | 입력이 같으면 성공 섹션을 보존하고 이어서 생성한다. |
| 모델·한도·통신 오류 | 트레이 원인 확인 → 연결/한도 복구 → 해당 작업 재요청. |
| 일반 문서 매칭 불충분 | 해당 제안 제외 후 등록 완료; 수동 매핑 가능. |
| 원본·평가 변경 | 이전 출력 보존, 최신 자료 반영 필요 표시. |
| 마이그레이션 실패 | API를 열지 않고 오류·권한 해결 후 재실행. |
| 디스크 부족 | 접수량을 줄이고 보존 정책에 따라 공간 확보; 볼륨 삭제 금지. |

## 자원과 보안

일반 업로드는 최대 4건을 처리한다. AI 요청은 프로세스별 제한에 더해 동일 DB에서 같은 API 키를 쓰는 모든 프로세스가 공유하는 4개 슬롯을 적용한다.
개발·QA·운영 DB는 분리되어 있으므로 서로의 예산을 공유하지 않는다. 같은 키를 별도 서비스에서 쓰는 호출까지 제한하는 공급자 계정 한도는 아니다.

기본값은 최근 24시간 키당 3,000요청·3천만 토큰·100달러, 계정당 60달러, 작업당 600요청·30달러·3,600초다.
가격을 확인할 수 없으면 새 요청을 보내지 않는다. 요청 전 보수적으로 예약하고 공급자가 사용량을 반환하면 정산한다.
통신 실패로 비용을 알 수 없는 요청은 무료로 처리하지 않는다. 일부 시각화 경로는 보수적 예약액을 유지한다.

분석/보고서 각 2개 슬롯은 프로젝트별로 번갈아 작업을 배정한다. 같은 프로젝트의 workflow 쓰기는 한 번에 하나만 허용한다.
각 슬롯의 리더 잠금과 heartbeat를 검사한다. 중단 작업은 저장 결과를 보존하고 사용자 재요청을 기다린다.

파싱은 별도 프로세스에서 메모리 512MB·CPU/벽시계 240초·최대 500 PDF 페이지 제한을 적용한다.
API 1.5GB, 등록 워커 2.5GB, 분석/보고서 워커 각 3GB와 CPU 2개 제한을 둔다. 한도 초과 파일은 사유를 표시하며 무한 대기하지 않는다.
주요 개발·운영 서비스 로그는 10MB × 3회 회전을 적용한다. DB·업로드 파일 용량은 별도 모니터링 대상이다.
운영 쿠키 기본값은 Secure이며 HTTPS가 필요하다. 기존 환경 파일의 명시적 설정은 자동 변경하지 않았다.
관리자 DB/초기화 비밀은 일회성 migrator만 받는다. 앱 DB 비밀번호를 별도로 분리했고 장기 실행 앱/워커는 UID 10001, 변환기는 1000, 웹은 nginx로 실행한다.
파일 권한 초기화만 네트워크 없는 일회성 root 컨테이너를 사용한다. Postgres는 공식 이미지의 초기화 후 postgres 사용자 실행 방식을 유지한다.
직접 Python 의존성 감사는 통과했지만 기반 OS의 미해결 CVE가 남았다. 구체적인 잔여 항목은 `improvements-20260925.md`에 기록한다.

## 백업·복원·마이그레이션

```powershell
./tools/ops/Backup-Environment.ps1 -Environment production
./tools/ops/Restore-BackupCheck.ps1 -BackupDirectory <백업 폴더>
```

백업은 쓰기 서비스를 잠시 멈추고 DB와 파일을 같은 시점에 저장한 뒤 정확히 그 컨테이너들을 재시작한다.
SHA-256 검사, AES-256-CBC 암호화와 HMAC-SHA256 인증을 적용한다. 키는 현재 Windows 사용자 DPAPI와 사용자/SYSTEM 파일 ACL로 보호한다.
백업 중 서비스 중단 시간이 생긴다. 암호화 키가 같은 호스트/사용자에 종속되므로 PC와 계정을 함께 잃으면 복구할 수 없다.
사용자가 별도 서버 백업을 제외했으므로 오프호스트 전송은 설정하지 않았다.

2026-09-25 격리 복원은 포트를 공개하지 않는 내부 네트워크와 별도 DB/파일 볼륨에서 검증했다.
개발 77문서/3계정은 12.16초, 운영 0문서/2계정은 9.22초에 해시 검사·복원·현재 마이그레이션·건수 비교를 통과했다.
이는 작은 로컬 데이터의 실측 복구 시간이며 운영 SLA가 아니다. 현재 백업은 수동/배포 전 실행이고 RPO는 마지막 성공 백업 이후 변경량이다. 일일 자동 백업 SLA는 없다.

SQL 마이그레이션 001~005는 적용 이력과 체크섬을 저장한다. 이미 적용한 SQL은 고치지 않고 다음 번호를 추가한다.
이전 DB의 최초 도입은 legacy baseline을 기록한다. 다운그레이드 SQL 대신 이전 이미지와 일관된 DB/파일 백업 복구를 사용한다.
앱 DB 비밀번호 분리 전 버전으로 돌아갈 때는 이전 앱 자격증명도 함께 맞춰야 한다. 실제 운영 데이터를 덮어쓰는 롤백은 실행하지 않았다.

## QA 재현

`Test-Service.ps1`은 이미지를 빌드하고 자동 검사를 실행한다. 외부 AI 키를 전달하지 않는다.
`qa_service_refactor.py`는 실제 HTTP/DB RLS/저장 파이프라인을 사용하고 AI 응답만 고정한다.
QA 워커를 멈춘 상태에서 QA 컨테이너로 실행하고 합성 계정 파일과 결과를 별도 마운트 경로에 저장한다.

`qa_workflow_recovery.py`는 prepare → API 재시작 → queued → 보고서 워커 시작 → verify 순서다.
과거 QA 작업을 정리하므로 다른 QA 작업과 동시에 실행하지 않는다.

`Run-SyntheticQAProbe.ps1 -Stage foundation|facts|dac|report|resume|export|gold|scope`는 합성 데이터만 실제 AI에 보낸다.
각 단계는 계획서·사업개요, 등록 사실, DAC, 27개 본문, 실패 부분 이어쓰기, HWPX 출력이다.
합성 계정 파일이 먼저 있어야 하며 API 사용료가 발생한다. 고객 원본을 이 경로에 넣지 않는다.
