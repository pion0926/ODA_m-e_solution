# 운영자·프로젝트·사용자 서비스 운영 구조

## 역할과 데이터 경계

- **운영자(admin)**: 프로젝트와 사용자 계정·접근 권한을 관리함. 업무 대시보드·분석·보고서 작성은 제공하지 않으며 관련 API도 차단함.
- **수행자(발급 계정)**: 관리자가 연결한 프로젝트만 접근함. 그 프로젝트의 문서·PDM·DAC·보고서를 사용함.
- **프로젝트**: 데이터 격리 단위임. 같은 프로젝트에 연결한 여러 수행자는 같은 사업 데이터를 공유함. 별도 고객 데이터는 별도 프로젝트로 발급해야 함.
- 한 계정에 여러 프로젝트가 필요한 경우 운영자가 추가 연결할 수 있음. 수행자는 상단 사업 전환에서 허용된 프로젝트만 선택함.

## 1. 신규 고객 발급

1. 관리자로 로그인하면 **프로젝트 관리**가 열림.
2. 프로젝트명을 입력하고 제공 언어를 선택하여 프로젝트를 생성함.
3. 이어지는 계정 발급에서 새 프로젝트가 선택되었는지 확인하고 아이디·표시 이름을 입력함.
4. 프로젝트 소속과 계정이 함께 저장됨. 잘못된 프로젝트는 계정만 남기는 부분 발급을 허용하지 않음.
5. 초기 비밀번호는 서버에서 생성하며 발급 직후에만 표시함. 창을 닫으면 다시 조회하지 못하므로 승인된 전달 수단으로 수령인에게 전달함.
6. 계정과 프로젝트는 기존 고객의 문서·평가·작성 본문을 복제하지 않음. 보고서의 27개 양식 정의만 빈 상태로 준비됨.

## 2. 권한·이용 상태 관리

- **사용자 관리**에서 프로젝트 필터/아이디 검색 후 선택한 계정의 표시 이름과 소속을 확인함.
- 메뉴별 작업 권한은 관리자 설정이 기준임. 보고서 권한을 제거하면 화면뿐 아니라 서버의 보고서 접근/생성이 차단됨.
- 이용 중지는 로그인 세션을 무효화하고 데이터는 유지함. 다시 활성화하면 동일 계정으로 이어서 사용함.
- 프로젝트 연결 해제 시 다음 요청부터 해당 프로젝트 접근이 취소됨. 자료 자체는 프로젝트에 남음.
- 비밀번호 재설정은 기존 세션을 폐기함. 운영자는 새 비밀번호를 적절한 별도 수단으로 전달해야 함.
- 사용자·프로젝트 삭제/백업·결제 기능은 이 화면의 구현 범위가 아님.

## 3. 수행자 작업 흐름

1. 로그인 → 빈 대시보드의 **자료 등록 시작**.
2. 원본 PDF/XLSX 등을 등록 → 추출·분류 완료 확인. 파일은 프로젝트 안에서 보관하며 같은 이름/내용의 중복 업로드는 기존 문서를 유지함.
3. **사업 개요**에서 최신 PDM 확인 → **성과지표 모니터링**의 지표 갱신. PDM의 OVI 목록과 같은 측정량의 실적만 연결함. 미확인은 0%나 사업 실패로 표시하지 않음.
4. **DAC 평가진단** 실행 → **분석 결과**에서 점수·내부 기준 적용·보완 근거 검토.
5. **보고서 자동작성**에서 섹션별 내용 생성 → 선택 섹션 AI 수정 요청과 rHWP 미리보기 → 전체 HWPX 변환·다운로드.

## 4. DAC 내부 점수 검토

- 서비스 범위: 적절성·일관성·효과성·효율성·지속가능성, 11개 질문.
- 각 질문에 1~4점 설명과 3개의 구체적 확인 기준을 둠. 확인 기준은 `config/dac_scoring_checks.json`에서 편집 가능함.
- 결과에는 확인 기준별 충족/일부 충족/미충족/미확인, 근거 설명, 선택 점수 이유, 상위 점수에 부족한 요건을 표시함.
- 자료 미확인은 실패 증거와 구분함. 미확인 항목이 포함되면 잠정 판단임을 표시함.
- 4점은 해당 질문의 4점 요건과 모든 내부 확인 기준 충족이 필요함.
- 버전은 각 평가 결과와 함께 저장함. 기준 변경 시 버전도 올리고 재평가해야 함. 과거 결과에 새 적용 내역을 만들어 붙이지 않음.
- 내부 1~4점은 OECD 공식 점수표가 아니며 AI 보조 분석은 평가자의 최종 검토가 필요함.

## 5. 추가 자료 등록

- 새 자료가 접수되면 기존 결과를 자동 삭제하지 않고 최신화 필요 상태로 구분함.
- 문서 처리 완료 → PDM 갱신 → DAC 재평가 → 보고서 재생성 순서를 따름.
- 자료 기준이 바뀐 상태에서는 과거 평가로 새 보고서를 정상 최신본인 것처럼 생성하지 못하도록 검사함.
- 기존 본문은 재평가만으로 덮어쓰지 않음. 보고서 재작성 요청 시 갱신함.

백엔드 파일의 축약 경로는 `redesign/backend/kodame_intake/` 기준임. 새 파일을 분리할 때는 Docker 포함 규칙과 빌드 시 정책 로딩 검사도 확인해야 함.

보고서 내용 생성과 변환은 분리하여 수정함. 생성부는 근거와 내용 계약을 검사하고, 변환부는 저장된 필드를 고정 양식에 배치함. JSON/구분자가 모호한 응답을 임의로 한 칸에 몰아넣지 않음. 표 분할 등 페이지 수를 바꾸는 수정 후에는 전체 HWPX를 다시 만들고 최종 조판 쪽수로 목차를 재검증해야 함. XML에 문장이 있다는 검사만으로 화면의 잘림이 없다고 판단하지 말고, 실제 rHWP의 표 하단과 다음 쪽 연결을 함께 확인함.

## 외부 제공 전 운영 조건

현재 시험 주소는 로컬 서비스임. 계정 기능 구현이 인터넷 공개 운영 완료를 의미하지는 않음. 외부 제공 전 HTTPS·보안 쿠키 설정, 강한 관리자 비밀번호, 비밀키 관리, DB/원본 문서 백업과 복원 시험, 보관·삭제 정책을 운영 환경에서 별도 확인해야 함. 공개 회원가입은 기본 비활성 상태를 유지함. 초기 비밀번호는 코드 저장소·QA 결과 문서에 기록하지 않음.
