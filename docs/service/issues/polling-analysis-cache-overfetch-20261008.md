# 상태 조회가 전체 분석 캐시를 반복 로딩하는 문제

## 원인과 영향

앱은 문서 목록·PDM을 3.5초마다 갱신한다. 목록 응답 자체는 요약됐지만 `SELECT *`가 문서의 전체 `analysis`를 먼저 DB에서 읽었다. PDM 목적매핑 검사 역시 DAC 원문 검토·측정 캐시가 포함된 전체 `analysis`를 읽었다. PDM 응답에는 서버 증분 분석용 `monitoring.pair_results`까지 포함됐다. 보고서가 최신 상태이면 대시보드는 12초마다 검토 승인 여부 확인을 위해 전체 문서·결과·보고서 bundle을 재생성했다.

운영 읽기 전용 크기 집계(원문·결과 수정 없음): 활성 문서 65건의 `analysis` JSON 텍스트 12,175,849바이트, 평가대상 62건은 12,172,551바이트였다. 후자 중 DAC 원문 캐시는 7,333,781바이트였다. 이 값은 DB JSON 텍스트 크기이며 HTTP 전송량·압축 후 크기·메모리 사용량을 뜻하지 않는다.

## 수정

- 문서 목록은 serializer에 필요한 상태·요약·분류 필드만 SQL에서 조회한다. 등록 사실 본문은 가져오지 않고 건수만 반환한다. 상세 원문·분석 조회는 기존 명시적 상세 API를 유지한다.
- PDM 문서 조회는 자동 목적매핑과 수동 포함/제외 판정에 필요한 필드만 받는다. v3 수동 지정 및 v4 목적 판정 규칙을 바꾸지 않는다.
- PDM 응답에서 내부 `pair_results`만 제외한다. 저장된 이력·증분 분석·현재 실적 근거·화면용 건수는 유지한다.
- 승인 이력이 아예 없으면 대시보드는 bundle 생성 없이 미승인으로 표시한다. 이력이 있는 경우에는 기존 전체 revision 검증을 유지해 이전 승인을 잘못 재사용하지 않는다.

동일 운영 데이터에 개선 SQL을 읽기 전용 적용한 결과, 목록의 `analysis` 조회는 1,825,385바이트(85.0% 감소), PDM의 `analysis` 조회는 64,520바이트(99.5% 감소)였다. 두 경로 합계는 약 24.35MB에서 1.89MB로 줄었다. PDM 응답에서 제외한 내부 pair 이력은 104,581바이트였다. 운영 DB나 캐시는 변경하지 않았다.

## 검증

QA PostgreSQL의 `jsonb_populate_record`로 합성 레코드만 조회했다. 문서 테이블을 읽거나 변경하지 않고 전체 조회와 projection 조회의 serializer 응답을 비교했다. 분석 없는 대기 문서, 빈 분석, 산출물 경고·등록 사실 건수, 자동 목적매핑, v3/레거시 수동 포함·제외를 확인했다. 내부 이력 제거가 원래 모델을 변경하지 않는지, 기존 승인이 있으면 정확한 revision 비교를 계속하는지도 검증했다.

`test_polling_read_models.py`, `test_pdm_evidence.py`, `test_performance_legacy_transition.py`, `test_frontend_v1_shell.py`: **66 passed**. SQL 검증은 격리 QA에서 `KODAME_POLLING_SQL_TEST=1`로 실행하며 기본 테스트는 DB에 연결하지 않는다. 외부 AI 호출 없음.

## 남은 범위

주기적 상세 갱신 자체는 유지한다. 향후 변경 revision 기반 상세 갱신, 비활성 화면의 주기 조절을 별도로 적용할 수 있다. 승인 이력이 있는 프로젝트의 bundle 재해시도 여전히 존재한다. 이를 캐시하려면 문서·PDM·규칙·보고서 변경의 무효화 계약부터 확정해야 한다. 시간만 기준으로 캐시해 승인 최신성을 훼손하지 않는다.

일반 목록/PDM/평가 상태 조회에서 원본 파일 재읽기나 AI 호출은 발견하지 않았다. 감사한 업로드 및 DAC 실행 경로도 LLM 호출 전에 DB 연결 범위를 종료한다. 이것은 해당 경로의 코드 검토 결과이며 전체 서비스의 부하 시험 결과는 아니다.
