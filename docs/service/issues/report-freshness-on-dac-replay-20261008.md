# 동일 DAC 전체 재사용 후 보고서가 다시 작성 대상으로 표시되는 문제

## 원인

DAC의 문서·모델·평가일·프롬프트·평가기준·선택 구간이 같으면 기존 평가 전체를 복사하여 새 실행 이력을 기록한다. 그러나 보고서 최신성은 실제 평가 실행 ID를 비교하므로 내용이 같은 검증된 전체 재사용도 이전 보고서를 무효화했다. 일반적인 실질 재평가에서 이전 보고서를 무효화하는 동작은 유지해야 한다.

## 수정

- `dac_replay`의 서버 전체 복사 경로에서만 `replay_basis` provenance를 생성한다. 원본의 assessment fingerprint, 문서 digest, workflow digest가 현재 입력과 모두 동일하고 값이 존재해야 한다. 사용자/AI 출력에서 proof를 가져오지 않는다.
- proof는 버전·새 실행 ID·프로젝트 ID·직전 원본 실행 ID·canonical 실행 ID·모델과 세 digest를 결합한다. snapshot을 만들 때 현재 완료행의 값과 대조하고, 같은 프로젝트의 원본 완료행도 조회하여 모델·세 digest를 확인한다. 잘못된 버전·복사된 다른 run ID·다른 프로젝트·변경된 입력·없는 원본은 공유 lineage로 인정하지 않는다.
- `evaluation_run_id`, `reused_from_run_id`, 완료시각과 출처 이력은 그대로 유지한다. 최신성 비교에만 서버가 검증한 `evaluation_basis_id`를 쓴다. 기존 보고서 snapshot에 basis가 없으면 원래 실행 ID를 기준으로 비교한다.
- 자료·workflow digest 비교는 계속 수행한다. 문서 추가/교체, PDM·프롬프트·규칙 변경, 모델·평가일 변경, 부분 질문 재사용 또는 실질 재평가는 기존 보고서의 현재성을 유지하지 않는다. 동일 숫자·동일 개수만으로 같은 평가로 취급하지 않는다.
- 보고서 재개/내보내기는 중앙 `snapshots_match` 정책을 사용한다. 변화이론 도식 캐시의 별도 실행 ID 해시도 같은 검증 basis를 사용한다. 원본 proof 조회는 필요한 세 digest만 읽어 전체 질문 checkpoint를 반복 로딩하지 않는다.
- 제출 검토 승인용 `current_bundle`은 실제 실행 이력까지 포함하는 기존 hash를 유지한다. 기존 제출 승인을 새 실행에 자동 승계하지 않는다.

## 검증

합성 회귀로 기존 보고서 snapshot과 새 검증 lineage의 일치, 연속 whole-run replay의 원본/직전 출처 이력, 잘못되거나 낡은 proof, 다른 프로젝트/모델의 원본, 없는 원본, 세 digest 변경·누락, 부분 질문 재사용, 모델·평가일·프롬프트·평가기준의 fingerprint 변경, 변화이론 캐시 재사용/무효화를 확인했다. 실제 전체 복사 함수가 서버 proof를 기록하고 원본을 변경하지 않는지도 검증했다.

관련 회귀 결과: **86 passed, 5 subtests passed**. 기존 목록 SQL의 격리 PostgreSQL 검증 7건은 이번 명령에서 opt-in하지 않아 skipped이며, 해당 목록 projection은 이전 별도 QA에서 실행·통과했다. 운영 데이터와 실행 중 평가를 변경하지 않았고 외부 AI를 호출하지 않았다. 실제 배포 여부는 릴리스 기록을 따른다.
